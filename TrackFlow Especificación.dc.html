TrackFlow · Sprint 1

Frontend: especificación y decisiones de diseño

Septiembre 2026
Prototipo HTML

TrackFlow conecta cada punto de tu cadena logística en un solo lugar: registra el envío, reporta su paso por cada centro de distribución y consulta el estado en tiempo real con tu número de guía.

1. Contexto

Sistema de registro y seguimiento de envíos. El backend está construido, probado end-to-end y desplegado: Spring Boot, monolito modular con ingesta por eventos (RabbitMQ), PostgreSQL sobre Supabase en producción. Este documento cubre únicamente el frontend.

Sprint 1 cubre tres historias de usuario: HU-01 registrar un envío (remitente + destinatario), HU-02 registrar un evento logístico (un punto de la cadena reporta un movimiento), HU-03 consultar el estado actual de un envío. Sprint 2 agrega HU-04 consultar el historial de movimientos y HU-08 iniciar y cerrar sesión.

2. Estado de la entrega

Prototipo funcional en un solo archivo, TrackFlow.dc.html, que consume la API real por red. No hay datos simulados: toda pantalla refleja lo que responde el backend, incluidos sus errores. La URL base es configurable; por defecto https://trackflow-mxll.onrender.com (despliegue del equipo, repositorio TrackflowFE/FabricaEscuela-Proyecto-TrackFlow), y se cambia a http://localhost:8080 para desarrollo local (requiere docker compose up -d y ./mvnw spring-boot:run).

Toda petición tiene tiempo límite: 25 s para la consulta de rastreo (tolera el arranque en frío de Render), 6 s para el autocompletado de ciudad, 10 s el resto. Si se agota, la pantalla muestra el error de red con opción de reintentar, nunca un spinner infinito.

4. Sistema visual

Color

Azul marino #14305c como estructura: nav, hero, pie. Naranja #f4711a reservado a las acciones — un solo botón naranja por pantalla. Fondo de trabajo claro #f2f2f3 en las pantallas interiores. Sin color decorativo fuera de esos dos.

Tipografía

Barlow Condensed en títulos, Barlow en texto, 16 px de base. Los números de guía van con cifras tabulares y tracking amplio para que se lean como un código.

Forma

Esquinas rectas, marcos de línea fina con marcas de registro en las esquinas, retícula visible de celdas iguales. Las tarjetas no llevan relleno: son dibujos de línea. El botón primario es el único objeto sólido.

Badges de estado

Registrado gris · En centro de distribución azul · En tránsito azul · En reparto ámbar · Entregado verde.

5. Reglas transversales de la API

  • Las escrituras son asíncronas: siempre 202 Accepted, nunca 201. No hay confirmación instantánea de que el dato ya existe.
  • El contrato está en inglés (rutas, campos y valores); los mensajes para el usuario siguen en español.
  • La ciudad es siempre un cityId numérico elegido por autocompletado, nunca texto libre.
  • documentType y documentNumber son campos separados, con validación por tipo.
  • No existe editar ni borrar: no hay PUT, PATCH ni DELETE. Corregir un error significa registrar un evento nuevo.
  • Las consultas del cliente (tracking, historial, ciudades) son públicas y se llaman sin token. Las de la operación (acciones disponibles, centros, reportes) exigen token de operador.
  • Todos los errores llegan en formato ProblemDetail (title, detail, status), incluido el 404 de tracking.
  • Todo error 400 trae un detail legible; la UI lo muestra tal cual, sin reemplazarlo por texto genérico.

6. Contrato consumido

GET /api/cities?q={texto} — público

Hasta 10 coincidencias (id, name, department, label), primero las que empiezan por el texto. Mismo catálogo para origen y destino.

POST /api/shipments — rol OPERADOR

sender y recipient con el mismo shape (fullName, documentType, documentNumber, phone, address, cityId) más description. Todos los campos obligatorios; la UI no envía la solicitud si falta alguno. Responde 202 con trackingNumber, eventId, recipient, destinationCity, requestedAt y processingStatus (QUEUED).

El trackingNumber lo genera el backend: el formulario no tiene campo de guía, es puro output, y es definitivo desde la respuesta aunque el registro siga procesándose. La UI muestra "procesando" y reintenta GET /api/tracking/{tn} cada 300 ms unos segundos para confirmar.

TipoFormato del número de documento
CC, CE6 a 10 dígitos
TI10 a 11 dígitos
PP5 a 15 caracteres, letras mayúsculas y dígitos
NIT9 a 10 dígitos; opcionalmente con dígito de verificación (890903938-8), validado contra las ponderaciones de la DIAN

El formato esperado se muestra dinámicamente bajo el campo según el tipo elegido. Los errores 400 llegan en formato ProblemDetail y, con campos faltantes, traen además missingFields (claves como sender.fullName); la UI marca cada campo.

POST /api/shipments/{trackingNumber}/events — rol OPERADOR

Tipos: RECEIVED_AT_CENTER, DISPATCHED, ARRIVED_AT_DESTINATION_CENTER, OUT_FOR_DELIVERY, DELIVERED. type y centerId obligatorios, delivererName obligatorio en OUT_FOR_DELIVERY, notes y occurredAt opcionales.

La UI envía la cabecera Idempotency-Key: si el registro falla por red y el operador reintenta, se reutiliza la misma clave y el backend devuelve el movimiento ya registrado en vez de duplicarlo. La clave se renueva al cambiar de guía, tipo o centro, y después de un registro exitoso.

Si no se envía occurredAt se asume que el movimiento acaba de ocurrir; el campo se diseñó opcional con "ahora" por defecto y ayuda explícita para reportes tardíos. Una fecha futura devuelve 400. Guía inexistente devuelve 404. Un evento con fecha anterior al último aplicado se guarda en el historial pero no cambia el estado visible del envío: la línea de tiempo lo marca como reporte rezagado.

GET /api/shipments/{trackingNumber}/actions — rol OPERADOR

Movimientos que el envío admite ahora (actions: type, label, expectedCity, centers, route), su currentStatus y su currentLocation. Alimenta el formulario de eventos para que el operador elija de una lista corta y correcta.

GET /api/tracking/{trackingNumber} — público

status, senderName, originCity, recipientName, destinationCity, registeredAt, lastMovementPoint, lastMovementAt y, solo cuando está entregado, recipientAddress. Guía inexistente devuelve 404, que la UI presenta como un estado amable y explícito, no como error crudo: "No encontramos ningún envío con ese número. Verifica que esté bien escrito", con el código de respuesta a la vista para diagnóstico.

GET /api/shipments/{trackingNumber}/events — público

HU-04. Responde { trackingNumber, totalMovements, message, movements }, con los movimientos ordenados por fecha real de ocurrencia (type, resultingStatus, point, cityName, notes, delivererName, occurredAt). Sin movimientos, message lo informa. Se renderiza como línea de tiempo vertical con ícono por tipo de evento.

POST /api/auth/login — público

Un solo formulario, sin selector de rol: el backend decide según las credenciales y el admin siempre incluye los permisos de operador ("ADMIN OPERADOR"). Body { username, password }; responde token, type, roles y expiresInSeconds. El JWT se guarda y se envía como Authorization: Bearer {token} solo en las peticiones protegidas. Credenciales incorrectas devuelven 401. Si el entorno no tiene credenciales configuradas devuelve 503 y se muestra el mensaje específico "No hay credenciales configuradas en este entorno", no un error genérico de usuario o clave. El claim de roles decide qué se muestra en la UI de operador, nunca antes del login.

GET /api/auth/sesion y POST /api/auth/logout — con token

HU-08. Al abrir la página, si hay un token guardado se valida con GET /api/auth/sesion; si responde 401 (sesión cerrada o inactiva más de 30 minutos) se descarta sin ruido. Cerrar sesión llama a POST /api/auth/logout, que invalida el token en el servidor, y además borra el token y los datos de operación de la pantalla. Cualquier 401 en una petición con token lleva al login con el aviso "Sesión terminada".

POST /api/admin/rebuild-projections — rol ADMIN

Sin body. Devuelve shipmentsRepublished y eventsRepublished. Pantalla simple, visible solo con rol ADMIN.

7. Estados diseñados

Cada pantalla cubre el camino completo, no solo el feliz: cargando, vacío (envío sin movimientos), error de red con reintento, 404 explícito, validación de formato en cliente antes de llamar al backend, 400 con el detail del backend y su lista de campos faltantes, 401/403 con invitación a iniciar sesión, 503 sin credenciales, y éxito 202 con aviso de procesamiento asíncrono.

9. Implementación prevista

Next.js 16 con App Router, React 19 y TypeScript; Tailwind CSS v4 con shadcn/ui estilo base-nova; primitivas Radix vía @base-ui/react, lucide-react para íconos y axios para HTTP.
